# System Design

## 1. 설계 목표
- 기준 상태 기능을 보존한다.
- 단일 `app.py` 구조를 당장 유지하되 기능 블록을 명확히 분리한다.
- SQLite + `sqlite3`를 유지하면서 관리자 검토 흐름, 가상 잔액 송금, 검색/필터, 보안 통제를 우선 추가한다.
- 상품별 1:1 문의와 문의 메시지 저장은 선택 기능으로 설계하고, 시간이 부족하면 제외할 수 있게 분리한다.

## 2. 상위 아키텍처
### 2.1 구성요소
1. **Web UI**
   - 기존 사용자 화면
   - 신규 관리자 화면
2. **Flask Route Layer (`app.py`)**
   - 인증/세션
   - 상품/검색
   - 신고
   - 송금
   - 관리자 기능
   - 선택 기능: 문의
3. **Socket.IO Layer**
   - 기존 공개 채팅 유지
   - 인증 및 rate limiting 추가
4. **SQLite Persistence**
   - 사용자, 상품, 신고, 송금, 감사 로그 저장
   - 선택 기능 구현 시 문의 스레드/문의 메시지 저장
5. **Security Controls**
   - 비밀번호 해시, CSRF, 권한 검증, 입력 검증, 안전한 세션 쿠키, 에러 처리, 감사 로그

## 3. 역할 기반 접근 모델
| 역할 | 권한 |
|---|---|
| `user` | 일반 기능 접근 |
| `admin` | 일반 기능 + 관리자 관리 기능 |
| `suspended` 상태 사용자 | 로그인/행위 제한 대상 |

### 핵심 원칙
- 인증과 역할 검증은 분리한다.
- 관리자 전용 라우트는 별도 가드로 보호한다.
- 초기 관리자 계정은 `getpass`를 사용하는 대화형 CLI `flask --app app create-admin`으로만 생성한다.
- 초기 관리자 계정은 코드나 DB에 하드코딩하지 않는다.
- 과제 범위에는 다른 사용자에게 관리자 권한을 부여하거나 회수하는 기능을 포함하지 않는다.
- 상품별 문의는 선택 기능이며, 구현할 경우에만 참여자 접근 제어를 적용한다.
- 관리자 제재는 상태 변경 + 감사 로그를 함께 남긴다.

## 4. 기능별 흐름
### 4.1 회원가입/로그인
1. 회원가입 요청 수신
2. 사용자명은 3~20자 영문/숫자/밑줄만 허용
3. 비밀번호는 최소 8자 이상만 허용
4. 신규 가입자 기본 가상 잔액은 `100000`으로 설정
5. 비밀번호 해시 저장
6. 로그인 시 해시 검증
7. 동일 IP + 사용자명 기준 10분 동안 5회 실패 시 로그인 시도를 제한
8. 정지 사용자는 신규 로그인을 차단한다.
9. 이미 로그인된 사용자가 정지되면 다음 보호 요청에서 세션을 종료한다.
10. 세션 생성 및 쿠키 보안 속성 적용

### 4.2 상품 등록/조회/검색
1. 로그인 사용자만 등록 가능
2. 상품 제목은 1~100자, 설명은 최대 2000자, 가격은 0 초과 정수만 허용
3. 검색어는 최대 100자, 최소/최대 가격은 정수이며 최소 가격은 최대 가격 이하만 허용
4. 상품 목록 화면에서 검색어 + 가격 범위 필터 처리
5. 차단된 상품은 일반 사용자 목록과 상세 조회에서 숨김

### 4.3 공개 채팅
1. 로그인 세션 확인
2. 채팅 메시지는 1~500자만 허용
3. 사용자당 10초 동안 최대 5개까지만 전송 허용
4. 전체 브로드캐스트

### 4.4 상품별 1:1 문의 (선택 기능)
1. Phase 7을 구현할 때만 상품 상세에서 문의 기능을 활성화한다.
2. 구매 희망자가 상품 상세에서 문의 시작
3. 판매자와 문의 생성자만 스레드 접근 가능
4. 메시지 저장 및 시간순 조회
5. 차단/정지 상태 사용자는 문의 작성 제한

### 4.5 신고 및 관리자 검토
1. 사용자 신고 제출
2. 신고 사유는 1~500자만 허용
3. 동일 사용자-대상에 대한 미처리 중복 신고 제한
4. 신고는 `pending` 상태로 저장
5. 관리자가 신고 검토 후 `dismissed` 또는 `actioned` 처리
6. 필요 시 사용자 정지 또는 상품 차단 수행
7. 처리 내역 및 관리자 작업 감사 로그 기록

### 4.6 가상 잔액 송금
1. 송금 요청 수신
2. 인증 및 입력 검증
3. 자기 자신/0 이하/잔액 초과 차단
4. 송금 메모는 최대 200자까지만 허용
5. 송금 row 저장
6. 송신자/수신자 잔액 갱신
7. 감사용 송금 내역 조회 가능

## 6. 템플릿 설계(예정)
### 기존 유지/확장

- `templates/dashboard.html`: 검색/가격 필터, 기존 공개 채팅 유지
- `templates/profile.html`: 잔액 정보 표시 가능
- `templates/report.html`: 신고 검증 메시지 강화

## 7. 공통 보안 설계
- 환경변수 기반 `SECRET_KEY`
- 비밀번호 해시 저장
- CSRF 토큰 검증
- 입력값 화이트리스트/길이/범위 검증
- 로그인/관리자/소유자 가드 함수 분리
- 세션 쿠키 옵션 강화
- 로그인/채팅 rate limiting
- 운영 환경 `debug=False`
- 예외 처리 및 일반 오류 화면
- 모든 관리자 조작은 감사 로그 기록

## 8. 설계상 주요 결정
1. **SQLite 유지**: 과제 범위와 현재 구조를 고려해 전체 ORM 전환은 제외한다.
2. **공개 채팅 유지**: 기존 요구 충돌 없이 보강만 수행한다.
3. **초기 관리자 생성은 CLI만 사용**: `flask --app app create-admin` 명령을 사용하고 `getpass` 기반 대화형 입력으로 비밀번호를 받아 해시만 저장한다.
4. **관리자 권한 부여/회수 기능 제외**: 과제 범위에 포함하지 않는다.
5. **상품별 문의는 선택 기능**: Phase 7에서만 구현하며, 미구현 시 필수 요구사항 미충족으로 보지 않는다.
6. **신고는 관리자 검토 후 제재**: 오탐과 남용을 줄인다.
7. **가상 잔액 송금**: 실제 결제 리스크 없이 요구사항 충족 가능하다.
8. **관리자 작업 감사 로그 필수**: 보안 과제 목적과 직접 연결된다.
